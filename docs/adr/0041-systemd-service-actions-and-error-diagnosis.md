# 0041. Aksi Layanan systemd, Status, dan Diagnosis Error

Melengkapi tab Services ([ADR 0040](0040-listening-port-owners-and-systemd-services-tab.md)) yang semula hanya-baca dengan dialog **Status & debug**, aksi start/stop/restart, dan panel **Probable causes** yang menjelaskan mengapa sebuah unit gagal.

## Konteks dan Masalah

1. Administrator yang melihat unit `failed` di Pantau harus membuka terminal hanya untuk menjalankan `systemctl status` dan `journalctl -u`.
2. Memulai ulang atau menghentikan layanan adalah tindakan paling umum setelah melihat daftar layanan, tetapi membutuhkan hak istimewa.
3. Log mentah panjang; penyebab umum (port bentrok, binary hilang, `User=` salah, batas restart) berulang dan dapat dikenali dari pola.

## Keputusan Arsitektur

1. **Detail** (`GET /api/hosts/{id}/systemd/detail?unit=…[&errors=1][&retry_sudo=1]`): satu perintah `sh -c` membaca `systemctl show` (properti terpilih), `systemctl status -l -n 0`, dan `journalctl -u … -n 200` (opsional `-p err`). Jurnal dibaca sebagai akun SSH dan, hanya bila hasilnya menunjukkan izin tidak cukup, diulang dengan `sudo -n`. **Backoff**: setelah sudo ditolak, sudo tidak dicoba lagi selama 24 jam (status di memori per Host, dibagi dengan pemindaian pemilik port pada inspeksi) agar host yang memerlukan kata sandi sudo tidak menerima catatan sudo-gagal pada setiap pembukaan dialog; selama backoff UI menjelaskan hal itu dan menyediakan tombol **Retry with sudo** (`retry_sudo=1`). Bila tetap tidak terbaca, UI menyarankan grup `systemd-journal` atau sudo tanpa kata sandi.
2. **Aksi** (`POST /api/hosts/{id}/systemd/action`): `start`, `stop`, `restart`, `reload`, `enable`, `disable`, `mask`, `unmask`, `reset-failed` pada satu layanan, serta `daemon-reload` untuk host (tanpa unit). `id -u` = 0 → langsung; selain itu `sudo -n`; bila sudo tidak tersedia → `systemctl --no-ask-password` polos (hanya berhasil bila polkit mengizinkan; pada pengujian dengan akun lokal tanpa hak sudo hasilnya `mode: none`, exit 1, dan pesan polkit asli "requires interactive authentication"). Aksi adalah permintaan eksplisit administrator sehingga sudo selalu dicoba (backoff hanya meredam probe otomatis) dan hasilnya memperbarui backoff. Mode (`root`/`sudo`/`none`) dikembalikan ke UI dan dicatat ke Activity Console (modul `systemd`), seperti jejak audit [ADR 0037](0037-elevated-file-manager-access.md). Tidak ada kata sandi yang diminta, dikirim, atau disimpan.
3. **Keamanan masukan**: nama unit harus cocok `^[A-Za-z0-9:_.@\\-]{1,200}\.service$` dan tidak diawali `-`; nilai di-quote dengan `shellQuote` di dalam skrip `sh -c`; aksi dibatasi pada daftar putih di atas. `stop`, `disable`, dan `mask` pada `ssh`/`sshd` ditolak server (HTTP 403) karena Pantau akan kehilangan akses (sekarang atau setelah reboot) dan tidak ditawarkan di UI; `restart` SSH diizinkan dengan peringatan tambahan di dialog konfirmasi. `mask` pada unit yang berkas aslinya ada di `/etc/systemd/system` ditolak oleh systemd sendiri (berkas tidak ditimpa) dan galatnya ditampilkan apa adanya.
4. **Keberhasilan semu**: `systemctl start/restart/reload` pada unit `Type=simple` dapat berhasil sebelum eksekusi gagal (mis. binary tidak ada). Setelah aksi itu skrip menunggu 1 detik lalu membaca `ActiveState`; hasil `failed` dilaporkan sebagai gagal dan UI membuka dialog debug otomatis. Untuk `reset-failed`/`enable`/`disable`/`mask`/`unmask`/`stop` status `failed` tidak dianggap kegagalan aksi.
5. **Diagnosis** (`diagnoseSystemd`, tanpa LLM/jaringan): aturan regex berurut spesifik→generik pada log + status + properti. Satu baris log dijelaskan sekali oleh aturan paling spesifik. Hanya unit bermasalah (failed, activating/deactivating, atau inactive dengan `Result` bukan `success`) yang dianalisis teksnya sehingga log lama pada unit sehat tidak disalahkan; unit sehat hanya dapat dilaporkan `restart_loop`. Bila tidak ada pola dikenali, hasil jatuh ke `exit_code` dengan `Result`/`ExecMainStatus` — tidak pernah mengarang penyebab. Backend mengembalikan kode stabil + baris bukti; judul dan saran diterjemahkan di UI (EN/ID).
6. **Konfirmasi dan umpan balik**: Restart, Stop, Disable, dan Mask memakai Confirmation Dialog; Start, Reload, Enable, Unmask, Reset failed, dan Reload systemd tidak. Aksi sekunder berada di menu **More** pada dialog; `Reload systemd` ada di header tab. Setelah aksi, daftar dan dialog dimuat ulang tanpa berkedip.

## Konsekuensi

- Satu klik dari unit gagal ke penyebab terkuat beserta kutipan log; seluruh siklus hidup layanan (jalan/henti, boot, mask, reset) tanpa membuka terminal.
- Aksi membutuhkan root atau `sudo` tanpa kata sandi pada host target; tanpa itu UI menampilkan galat polkit asli dan penjelasan kebutuhan hak akses.
- Probe sudo otomatis dibatasi satu kali per 24 jam per Host setelah penolakan; percobaan sudo yang gagal tetap dapat tercatat di log autentikasi host (pada sistem uji Arch dengan sudo 1.9 percobaan `sudo -n true` yang ditolak tidak menghasilkan entri jurnal, tetapi konfigurasi `log_denied`/auditd lain dapat mencatatnya).
- Perubahan isi unit file (mengedit `ExecStart` dan sejenisnya) tetap dilakukan lewat terminal atau File Manager; setelah itu gunakan **Reload systemd**.
